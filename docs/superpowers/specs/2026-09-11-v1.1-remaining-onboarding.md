## What the app is

trackit — a voice-first iPhone app for logging resistance-training workouts. The
lifter holds a talk button, speaks a set ("225 for 5"), releases; the app
recognises it on-device, parses it, records it, and confirms by voice + haptic.
Fully offline. iOS 17+. Forced dark. Ships under the placeholder name "Trackit".

v1 (subsystems A–F) is complete and merged. v1.1 is a roadmap of 7 clusters in
`docs/superpowers/specs/2026-09-06-v1.1-deferred-work-design.md`. Clusters 1–4
are merged. What remains: **Cluster 5** (device verification + two small code
pieces), **Cluster 6** (accuracy launch gate), **Cluster 7** (7 named product
features, each needing its own design pass). The `2026-09-11-cluster-*` specs
cover exactly that remainder.

## The three layers and what "done" means in each

| Layer | Build & test | "Done" = |
|---|---|---|
| `WorkoutLoggerCore` | `cd Packages/WorkoutLoggerCore && swift test` | new behaviour covered by `swift test`, green |
| `WorkoutLoggerApp` | `cd Packages/WorkoutLoggerApp && swift test --no-parallel` | new behaviour covered against fakes, green |
| `App/` | `xcodegen generate && xcodebuild …` (needs a Mac + Xcode 26) | compiles; **behaviour is verified on a device**, not here |

### `App/` is "files-only" in this environment

The `App/` target is **not compiled by SwiftPM**. On a machine without Xcode you
can still *edit* `App/` files — they are consistency-checked by eye against the
package API they call — but you cannot build or run them. Treat every `App/`
change as: "does this call the package surface correctly?" and defer "does it
actually work" to a device pass. The `2026-09-11-cluster-5-*` spec is where those
device passes are catalogued.

If you *do* have a Mac with Xcode 26 / iOS 26 SDK: `xcodegen generate` then
`xcodebuild -scheme Trackit -destination 'generic/platform=iOS' build`.

## Non-obvious conventions (these have bitten past contributors)

1. **`swift test` deadlocks the App package.** The default parallel swift-testing
   runner freezes the `WorkoutLoggerApp` suite on this project (hangs at ~0% CPU
   mid-run). Always `swift test --no-parallel` for that package. It runs the same
   ~245 tests clean in <0.5 s. The Core package is fine with plain `swift test`.

2. **The Bash working directory persists between commands.** A compound command
   ending in `cd <repo-root>` (common before a `git commit`) leaves the next
   `swift test` in the wrong directory — you'll see "Could not find Package.swift"
   or a test count from the wrong package. Always `cd` explicitly into
   `Packages/WorkoutLoggerCore` or `Packages/WorkoutLoggerApp` before a package
   command.

3. **CoreData "corrupt store" log lines in an App test run are expected.** There
   is an intentional decode-failure test (`SwiftDataWorkoutStore` degraded-load
   path) that logs `NSCocoaErrorDomain 259 / "Store failed to load"`. It is not a
   failure — check the final `Test run with N tests … passed` line.

4. **SourceKit shows phantom errors on package + `App/` files** — "No such module
   'Testing'", "No such module 'WorkoutLoggerCore'", "Cannot find type …". These
   are stale-indexer noise. The real `swift build` / `swift test` is the source of
   truth; if it's green, the file is fine.

5. **Test baselines as of the Cluster 4 merge (`68f61b9`, 2026-09-10):**
   Core **150**, App **245**. State the new counts in each commit message.

6. **The core package is "frozen" except by explicit budget.** Historically each
   subsystem got a named budget of "N additive Core edits" and nothing more.
   Clusters 1–4 spent theirs. If a Cluster 5/6/7 task needs a Core change, that is
   a design decision to call out in the spec's open questions, not something to
   slip in.

7. **ADRs are binding.** ADR-0001: a Set has four orthogonal axes (load type,
   effort measure, role, grouping) — never collapse them. ADR-0002: loads are
   canonicalised to kilograms inside `WorkoutEngine`. ADR-0003: estimated 1RM is
   Epley (`load × (30 + reps) / 30`). Do not re-litigate these.

8. **Naming follows `Packages/WorkoutLoggerCore/CONTEXT.md`.** It has an explicit
   `_Avoid_` list per term (e.g. never "session" for a Workout, never "PB" for a
   personal record). Test names and identifiers use that vocabulary.

9. **Do not commit** `graft/`, `.impeccable/`, `.superpowers/`, `Trackit.xcodeproj`,
   `.build/`. `.gitignore` covers most; `.impeccable/` is an open question, leave
   it untracked.

## Working rhythm (TDD → review → finish)

This project was built with the `mattpocock-skills` and `superpowers` Claude Code
skills. If you have them, invoke them. If you don't, the manual equivalents are:

### TDD (`mattpocock-skills:tdd`)

- One **vertical slice** per cycle: one seam, one failing test, the minimum code
  to pass it, then stop. Do not write a batch of tests up front.
- **Red before green** — run the new test, watch it fail for the expected reason,
  then implement.
- **Refactoring is a separate stage** — never mixed into the red→green step. It
  happens when you fold review findings (below).
- Commit per slice. Small commits. Conventional-commit style (`feat(scope): …`,
  `test(scope): …`, `refactor(scope): …`, `docs(scope): …`).

### Two-axis code review (`mattpocock-skills:code-review`)

After the feature is built, before opening the PR: review the whole branch diff
against a **fixed point** (the commit the branch started from) on two axes,
ideally as two independent reviewers so they don't cross-contaminate:

- **Standards** — does the diff follow the repo's conventions and avoid the
  Fowler code smells (Mysterious Name, Duplicated Code, Feature Envy, Data Clumps,
  Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change,
  Speculative Generality, Message Chains, Middle Man, Refused Bequest)? This repo
  has **no coding-standards file**, so every Standards finding is a judgement
  call, not a hard violation.
- **Spec** — does the diff implement exactly what the originating spec asked, no
  more (scope creep) and no less (missing / partial / wrong)?

Fold the findings worth taking as a single `refactor(scope): fold … review`
commit. Note in it which findings you took and which you consciously skipped.

### Finish the branch (`superpowers:finishing-a-development-branch`)

1. Full suite green on the branch tip (both packages).
2. `git push -u origin <branch>`.
3. `gh pr create --base main …` with a body that summarises what changed, the
   review outcome, and the new test counts.
4. `gh pr merge <#> --rebase --delete-branch` (this project rebase-merges — no
   merge commits).
5. Resync local main: `git checkout main && git fetch origin && git reset --hard
   origin/main`. Delete the local branch, prune stale tracking refs.
6. Update the cluster spec's "Status" block (and, if you keep an agent memory
   file, `phase-progress.md`).

### Branching

Never work on `main`. Branch first: `git checkout -b v1.1-cluster-<n>-<slug>`.
