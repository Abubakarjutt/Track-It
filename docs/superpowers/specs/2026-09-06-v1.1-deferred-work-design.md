# v1.1 — Deferred Work (carried gaps from v1 subsystems A–F)

**Date:** 2026-09-06
**Status:** draft, pending user review
**Scope:** the work consciously deferred out of the v1 build, gathered from the
five subsystem specs (A+B, C, D, E, F) and the master spec
`Packages/WorkoutLoggerCore/specs/v1-voice-logging.md`. This is a roadmap spec,
not a single-subsystem design. Each cluster below names its source deferral and
is sized to be its own implementation cycle.

**Builds on:** all of v1, merged to `main` (subsystem F at `48b99ca`).
Core 124 tests / App 186 tests green. `WorkoutLoggerCore` is otherwise frozen.

## Context

v1 shipped every user story in `specs/v1-voice-logging.md` and all six subsystem
specs. What is left is not new product scope — it is the set of small cuts each
subsystem made on purpose, recorded in its "Out of Scope" and "Further Notes"
sections with a one-line rationale, plus the launch-gate instrumentation the
master spec always framed as "tracked metric first, hard gate later."

The cuts fall into seven clusters:

1. **Core seam debt** — a bundle of additive `WorkoutLoggerCore` changes each
   subsystem declined to make mid-cycle because the core was frozen to an
   agreed per-subsystem edit budget.
2. **Templated-workout durability across a relaunch.**
3. **Post-workout editing completeness.**
4. **HealthKit hardening** — cross-launch dedupe, re-sync of edited workouts.
5. **Device / integration verification** — nothing below the SwiftPM seam has
   ever been built or run in this environment; plus the two unwritten pieces of
   new code (the telemetry transport, the latency instrumentation).
6. **Launch-gate accuracy metric** — the audio-corpus rate against the real
   recogniser.
7. **Product v1.1 items already named in the master spec** (CloudKit, earbud
   button, Live Activity, grammar long-tail, light mode, Watch complication) —
   listed here for completeness, specified elsewhere.

## Problem Statement

Three things are true at once:

- **The stored record is always correct.** Every carried gap is in a
  *presentation*, *durability*, or *verification* layer, never in what gets
  written to SwiftData. No deferral here can corrupt a logged workout.
- **A first-time iOS developer has never run the app.** The `swift test` suites
  cover the parser, the engine, the session model, every projection, and the
  export / HealthKit / telemetry builders. The Xcode target under `App/` — the
  view tree and the `System*` framework wrappers — has never been through
  `xcodebuild` here. Real speech recognition, TTS, haptics, and HealthKit writes
  are unproven.
- **The launch gate is asserted against hand-authored data.** `CorpusScore`
  checks a ≥ 85% no-correction rate over 14 rows of hand-written recogniser
  hypotheses. The real recogniser has never fed it, and the ≤ 3 s median
  press-to-confirmed-set latency is not measured anywhere.

## Solution

Seven cycles, each merging only once its own package tests are green, matching
the D/E/F cadence. Order is by dependency and risk, not by size:

| # | Cluster | Depends on | Where it runs |
|---|---|---|---|
| 1 | Core seam debt (single core-reopen pass) | — | `swift test` |
| 2 | Templated-workout durability across relaunch | 1 (template identity on `Workout`) | `swift test` |
| 3 | Post-workout editing completeness | 1 (run-id addressing) | `swift test` + app |
| 4 | HealthKit hardening | — | `swift test` + device |
| 5 | Device / integration verification + telemetry transport + latency instrumentation | — | Xcode + device + backend |
| 6 | Launch-gate accuracy metric (corpus vs real recogniser) | 5a (recogniser front-end) | CI + device |
| 7 | Named product v1.1 items | per-item | own specs |

Cluster 5 is the true blocker on shipping and should start first in wall-clock
terms even though clusters 1–4 are logically independent of it.

## Cluster 1 — Core seam debt (one core-reopen pass)

`WorkoutLoggerCore` was frozen to an additive edit budget in every subsystem
(A+B: `: Codable` only; D: two edits — `movingSet` plus the mid-workout edit
seam; E/F: none). Six changes were named across three code reviews and
deliberately not taken. Do them together, once, so the core is opened and
re-frozen a single time.

### 1a — Re-seed the in-session personal-record bar

**Source:** subsystem D, "Out of Scope" item 3 and "Further Notes → Personal-record
bar residue."

`WorkoutEngine` seeds `knownBests` / `bestOneRepMax` from launch-time history at
the start of each workout. A lifter who completes two workouts without relaunching
and sets a new estimated-1RM record in the first has the second workout's sets for
that exercise judged against the *pre-first-workout* best. The stored
`PersonalRecord` is always correct; only the same-session celebration (haptic +
trophy) can be over- or under-eager.

**Fix:** on `startWorkout()` / `startWorkout(from:)`, re-derive `knownBests` from
the injected history closure (already available to the model as of subsystem D)
rather than from a value captured at launch. One-line change plus a test:
workout A sets a record for an exercise → workout B in the same session, a lesser
set on that exercise is *not* flagged, a set beating A's value *is*.

### 1b — Feed `WorkoutContext.previousSet` from `hear`

**Source:** `phase-progress` (Phase 3): "`WorkoutContext.previousSet` still `nil`
from `hear`."

The parser accepts a `previousSet` for the active exercise but the engine never
supplies it — `WorkoutEngine.hear` always passes `WorkoutContext(unit:)` with
`previousSet: nil`. Any grammar that leans on the previous set (relative phrasing
in cluster 7's long-tail, a tighter repeat-to-retry tolerance) is impossible
until this is wired.

**Fix:** `hear` looks up the last `LoggedSet` on the active entry and passes it
in. Behavioural test: an utterance whose interpretation differs given a previous
set (once such a rule exists) resolves correctly; until then, assert the context
is populated via a parser spy.

### 1c — Parser confidence on confident results

**Source:** master spec readback bullet (~line 397) and its reconciliation note;
`phase-progress` (Phase 3); subsystem A+B.

`readbackStyle(for:isNewExercise:capAtEarcon:)` originally took a `confidence`
parameter. It was dropped because the parser only reports a confidence score on
`.lowConfidence` — there is no producer for a confidence on a confident `.set` or
`.announcement`. Story 20 ("terse when confident, fuller when unsure") is
therefore only half-implemented: it upgrades to full TTS for a *new* exercise but
never for a *shaky* parse of a known one.

**Fix:** the parser reports a confidence score on `.set` and `.announcement`
results. Re-add the threshold check in `readbackStyle` so a low-confidence parse
of a known exercise also forces full TTS. Table-driven parser tests for the score;
a `readbackStyle` case for the shaky-known-exercise path.

### 1d — `Exercise: Hashable`, kill the stringly-typed maps

**Source:** `phase-progress` (carried across Phase 3, Phase 4, and the subsystem D
review): `knownBests`, `bestOneRepMax`, and `templateRestTargets` are all
`[String: …]` keyed on `exercise.name`.

Name-keying is a latent correctness bug: two library exercises that normalise to
the same display name, or an alias drift between a stored entry and the current
library, collide or miss silently. Subsystem D's "Further Notes → Progress and
badge lookups use whole-value exercise equality" documents the read-side version
of the same hazard.

**Fix:** conform `Exercise` to `Hashable` (public-API change — hence deferred out
of every prior cycle) and key the three maps on the value. Round-trip and
collision tests.

### 1e — Split `WorkoutEngine` into composed types

**Source:** `phase-progress` (Phase 3 review, carried): extract `RestTimer` and a
personal-record tracker from `WorkoutEngine`.

`WorkoutEngine` owns workout lifecycle, parser-result application, load
canonicalisation, PR detection, *and* rest-timer state. The rest-timer methods
(`startRest`, `skipRest`, `restElapsedSeconds`, `isRestTargetReached`,
`currentRestTargetSeconds`, `templateRestTargets`) and the PR methods
(`recordPersonalBest`, `recomputeBest`, `knownBests`, `bestOneRepMax`) are two
cohesive sub-machines that can move behind their own types without changing the
engine's public surface.

**Fix:** mechanical extraction, behaviour-preserving, existing engine tests stay
green unchanged. Do this *after* 1a and 1d so the extracted types are born clean.

### 1f — Small carried findings

**Source:** `phase-progress` (subsystem D review, "Findings NOT taken").

- `ExerciseSession` / `ExerciseProgress` stored fields `var` → `let`.
- `estimatedOneRepMax(of:)` overload rename (ambiguous with
  `estimatedOneRepMax(loadKilograms:reps:)`).
- `workoutTemplate(from:named:)` round-trip currently drops rest targets — a
  completed workout has none, but once cluster 2 records template identity the
  round-trip should carry them.
- No template identity on `Workout` — **required by cluster 2**, so land it here.

### Cluster 1 out of scope

- Any behaviour change to load canonicalisation, the four-axis model, or the
  Epley formula (ADR-0002 / ADR-0003 stand).
- An LLM parser fallback (master spec "Not planned").

## Cluster 2 — Templated-workout durability across a relaunch

**Source:** subsystem C, "Further Notes → Template rest targets across a relaunch";
subsystem A+B deferrals.

`WorkoutEngine.resume(_:)` adopts a stale not-yet-ended workout at launch. It
deliberately clears `restStartedAt` (story 20 — a resumed workout shows no rest
until the next set; keep this). It *also* drops `templateRestTargets`, because
those are armed from a `WorkoutTemplate` value that no longer exists after a
relaunch. A lifter who forgot to end a templated workout, let it go stale, and
resumed it loses every per-exercise rest target until they re-announce each
exercise.

**Fix (depends on cluster 1f):** record the originating template's identity on
`Workout` at `startWorkout(from:)`. On `resume`, re-load that template through the
injected library/template handle and re-arm `templateRestTargets`. Test: start
from a template with a non-default rest target on squat → simulate relaunch →
`resume` → `currentRestTargetSeconds` for squat is the template's value, not
`defaultRestTargetSeconds`, before squat is re-announced.

### Cluster 2 out of scope

- Persisting the full template body on the workout (identity + a re-load is
  enough).
- Surviving a template the user deleted between sessions (fall back to the
  default, as today).

## Cluster 3 — Post-workout editing completeness

**Source:** subsystem D, "Out of Scope."

Subsystem D's set editor covers load, reps, role, grouping (clear-to-straight or
mark-as-dropset), and note. The following corrections were cut:

| Gap | Detail | Rough size |
|---|---|---|
| **Join a set into a superset run** (story 26, second half) | The grouping control can *clear* a superset marker but not assign a set into a specific run — it has no run-id to choose. Needs a run picker on the detail screen backed by `LoggedSet.supersetRunID`. | 1 core transform + UI |
| **Edit effort measure / load type** | Changing an already-recorded set from reps to duration, or external to assisted, is not a v1 correction path. | 1 core transform + UI |
| **Delete an entire workout** from the history list | No delete affordance on the history list; only per-set removal inside a workout. | UI + store method |
| **Standalone exercise picker for progress** | The progress screen is reachable only from a set on a completed-workout detail screen. A browse-all-exercises entry point was deferred. | UI only |
| **Chart interactions** | Zoom, scrub, date-range selection, per-metric toggles. Charts currently render fixed series over all history. | UI only |
| **Undo/redo of edits** | An edit is immediate and corrected only by another edit. | model + UI |

**Shape:** unchanged from subsystem D — pure transforms in the core (or pure
projections in the app), one `@Observable @MainActor` model per screen area, dumb
SwiftUI views. The run-picker and effort-measure edits are the only two needing a
core transform; the rest are app-layer.

### Cluster 3 out of scope

- Cross-exercise set moves during an *active* workout (completed-workout action
  only, as in v1).
- Bulk edits across workouts.

## Cluster 4 — HealthKit hardening

**Source:** subsystem F, "Out of Scope" and "Further Notes."

v1's HealthKit writer is one-way, writes once per workout on end, and dedupes
**only within a session**. Two gaps:

- **Cross-launch persistent dedupe.** If the app is killed after a workout is
  written to Health but before some later bookkeeping, a relaunch path that
  re-writes completed workouts would double-post. v1 accepted this — "the worst
  case is a duplicate HKWorkout the user deletes in the Health app." A persistent
  record of which `Workout.startedAt` values have been synced closes it.
- **Re-syncing an edited past workout.** A workout corrected on the detail screen
  (cluster 3, or v1's existing editor) is never reflected in Health. Needs the
  persistent sync record from the previous bullet plus an update/delete-and-rewrite
  path against `HKWorkout`.

**Fix:** add a `syncedWorkouts` persistent set (its own tiny `@Model`, keyed on
`startedAt`, mirroring `SettingsStore`'s bucket style). The writer checks it
before writing and records after. An edit to an already-synced workout enqueues a
re-sync. Package tests over a fake `HealthKitWorkoutStore` (already exists):
write once → second attempt no-ops; edit → re-sync fires with the new duration.

### Cluster 4 out of scope

- Two-way HealthKit (reading bodyweight or external workouts) — master spec, hard
  boundary.
- Per-set HealthKit samples, heart rate, workout routes.

## Cluster 5 — Device / integration verification, telemetry transport, latency instrumentation

**Source:** every subsystem spec's "Testing boundary" / "not `swift test`-covered"
table (5a); subsystem F "Out of Scope" (5b); master spec "Success gates" (5c).

Nothing in `App/` has been built or run in this environment. Most of this cycle
is not new code — it is standing up an Xcode + device loop and closing what only
a real build can close. Two parts (5b, 5c) *are* new code: the telemetry
transport the F spec left unspecified, and the latency instrumentation the master
spec's launch gate needs.

### 5a — Stand up the Xcode + device loop

- **`xcodegen generate` → `xcodebuild`** on `project.yml` actually produces a
  running app. First real compile of the whole view tree and the `System*`
  wrappers.
- **`SystemSpeechRecognizer`** — real `SFSpeechRecognizer` + `AVAudioEngine`
  with `requiresOnDeviceRecognition = true`, n-best shape, `.dictation` hint,
  behaviour in gym noise. The master spec's whole premise.
- **`SystemReadbackVoice`** — `AVSpeechSynthesizer` timing and the earcon via
  `AudioServicesPlaySystemSound`, felt between sets.
- **`SystemHaptics`** — the four-pattern `CHHapticEngine` set (logged /
  notCaught / personalRecord / restReached) actually feels distinct.
- **`SystemHealthKitWorkoutStore`** — a real `HKWorkout` write, the authorization
  sheet, the opt-in flow from Settings.
- **The "couple of" UI tests** the subsystem C spec and the master spec's "UI
  tests" section both promise: a HUD glanceable-state snapshot and a tap-select
  interaction check. `TrackitTests` is a near-empty target today.
- **Keep-awake, portrait lock, Dynamic Type on the big HUD number, Reduce
  Motion** (stories 42, 66, 67) — asserted in projections, never seen on a
  screen.

**Process:** `swift test` stays the inner loop; `xcodegen && xcodebuild` plus a
device smoke test at each milestone, as the A+B spec's "Process" section always
intended.

### 5b — Telemetry transport

**Source:** subsystem F, "Out of Scope" ("The analytics backend and transport —
the `System` sink's networking is an implementation detail, not specified here")
and "Further Notes → Privacy stance."

Everything above the wire is built: `TelemetryEvent` (the closed enum that is the
structural guarantee against content leakage), `TelemetryRecorder`, the local
queue, the opt-in flag defaulting to `false`, and the `TelemetrySink` protocol
with its fakes. The one unimplemented piece is `SystemTelemetrySink` — the
concrete type that batches queued events and sends them.

To decide and build:

- **Endpoint + provider.** A first-party endpoint, or a hosted analytics service.
  The payload is a small fixed JSON array of the enum's cases plus a
  content-free install id. No audio, no names, no loads, no transcripts — the
  enum makes any other shape unrepresentable, and that invariant must survive
  the serializer (a test asserts the encoded payload contains only enum-derived
  keys).
- **Batching + retry.** Flush on a size or time threshold; retry with backoff;
  drop the queue if it exceeds a cap rather than growing unbounded. Never block
  the logging loop — the send is fire-and-forget off the main actor.
- **Offline.** The queue already persists locally; the sink no-ops cleanly with
  no connectivity and flushes on the next opportunity. This must not
  re-introduce a network dependency into the core loop (`PRODUCT.md`'s permanent
  on-device commitment).
- **Opt-out semantics.** Turning the flag off stops future sends and discards the
  pending queue.

Package-testable against a fake URL protocol / injected transport: batch fires at
the threshold, retries on a 5xx, drops past the cap, payload shape is
enum-only, flag-off clears the queue.

### 5c — Latency instrumentation

**Source:** master spec, "Further Notes → Success gates" (≤ 3 s median
press-to-confirmed-set) and "Testing Decisions → Slower / metric tests."

The ≤ 3 s median press-to-confirmed-set latency is not measured anywhere. Add a
timing seam around the session model's `released()` → readback path:

- **The measured span** is button-release to the moment the "logged" haptic /
  readback fires — the point the lifter knows the set is in. It covers
  `endUtterance()`, `postProcess`, `parse`, `engine.hear`, and feedback
  dispatch.
- **In tests**, the injected clock already drives the session model; assert the
  computed span for a scripted utterance and that the median over a batch is
  reported.
- **On device**, wall-clock the same span and surface it. The natural carrier is
  a `TelemetryEvent` case (`setLoggedLatencyMillis`) so 5b's transport reports it
  from real usage — this is why 5b and 5c ship together. Bucketed to the nearest
  100 ms; still no workout content.
- **The gate.** Report the median as a tracked metric first (matching how the
  corpus no-correction rate is treated); promote to a hard pre-release check
  once it is stably under 3 s on real hardware.

### Cluster 5 out of scope

- Rewriting any logic that already passes `swift test` — 5a is verification and
  wiring, not redesign.
- Field aggregation / dashboards over the latency and telemetry stream (the sink
  sends; fleet analysis is later).
- Per-stage latency attribution (recogniser vs parse vs dispatch) — one span is
  enough for the gate.

## Cluster 6 — Launch-gate accuracy metric

**Source:** master spec, "Testing Decisions → Slower / metric tests → Audio
corpus run"; `phase-progress` (Phase 5).

This cluster is now just the **accuracy** half of the launch gate; the latency
half moved to cluster 5c (it ships with the telemetry transport that carries it).

The package slice exists: `CorpusScore.score([CorpusEntry], library:)` runs canned
recogniser n-best through the real `postProcess → parse` chain and reports the
no-correction rate, with a ≥ 0.85 floor asserted as a tracked metric.
`CorpusScoreTests` currently scores 1.0 — on **14 hand-authored rows**.

What is missing, blocked on cluster 5a's recogniser front-end:

- **Real hypotheses.** Swap the hand-written n-best lists for output from the real
  on-device recogniser over recorded clips (self + volunteers, real gym noise),
  covering every axis combination and command. Then promote the assertion from
  tracked-metric to a hard CI gate once the rate is stable above 85%.

The retention and PMF gates (≥ 40% complete 3 workouts in 2 weeks; ≥ 40%
"very disappointed" to lose it) are beta-cohort measurements, not code — noted
here so the gate list is complete.

### Cluster 6 out of scope

- The latency gate — now cluster 5c.
- A field dashboard over the corpus rate; CI tracking is enough.

## Testing Decisions

Unchanged from v1: assert external behaviour at a seam, never internal call
order or view hierarchy. Clusters 1–4 and 5b/5c add cases to the existing
`swift test` suites in `WorkoutLoggerCore` and `WorkoutLoggerApp`. 5a and
cluster 6 add the device and CI layers the v1 specs always scoped as "deferred —
needs `xcodebuild` / device."

New coverage by cluster:

- **1** — re-seed test (workout A → workout B, same session); `previousSet`
  populated; parser confidence score on confident results + the shaky-known
  `readbackStyle` case; `Exercise: Hashable` round-trip + collision;
  engine tests unchanged after the `RestTimer` / PR-tracker extraction.
- **2** — template rest target survives a simulated relaunch.
- **3** — one core transform test each for run-join and effort-measure edit;
  app-model tests for workout delete and undo/redo.
- **4** — sync-once / no-op-twice / re-sync-on-edit over the fake HealthKit store.
- **5** — 5a: the first real `xcodebuild`, the two promised UI tests, a device
  smoke checklist. 5b: telemetry batch fires at threshold, retries on 5xx, drops
  past cap, payload shape is enum-only, flag-off clears the queue. 5c: computed
  press-to-logged span for a scripted utterance, median reported over a batch.
- **6** — corpus fed by real recogniser output; no-correction rate holds ≥ 85%.

## Further Notes

- **One core-reopen.** Cluster 1 exists as a bundle specifically so
  `WorkoutLoggerCore` is unfrozen and re-frozen once. Landing 1a–1f piecemeal
  across later cycles is how the stringly-typed maps survived three reviews.
- **Cluster 5 gates the ship, clusters 1–4 do not.** The stored record is correct
  today. Cluster 5 holds the only genuinely unwritten code left in the app (5b
  the telemetry transport, 5c the latency timing seam) plus the proof that the
  app *runs* and clears its accuracy gate on real hardware. In wall-clock terms
  it should start first.
- **5b and 5c ship together.** The latency seam's natural carrier off-device is a
  content-free `TelemetryEvent` case, so it needs 5b's transport to be useful in
  the field. Building them in one cycle keeps the payload-shape invariant test in
  one place.
- **`resume` still clears `restStartedAt` on purpose.** Cluster 2 re-arms
  template rest *targets*, not the running rest clock — story 20 stands.
- **No issue tracker.** This repo tracks specs as files (every prior spec says
  so). This doc is the backlog; there is nothing to file. Next step per cluster:
  `writing-plans` then subagent-driven execution, as subsystems C–F were built.
